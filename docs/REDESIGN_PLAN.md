# Steam 시장 트렌드·장르 잠재력 분석 도구 재설계 계획

## 1. 목표 정의

이 프로젝트는 게임 개발자가 개발하려는 게임의 장르, 태그, 가격, 플랫폼, 언어, 기능 정보를 입력하면 Steam 및 외부 시장 데이터를 기반으로 다음을 제공하는 정적 HTML 웹사이트를 만든다.

- 선택한 장르/태그가 현재 시장에서 트렌드인지
- 유사 게임 대비 성공 가능성과 잠재력이 어느 정도인지
- 해당 장르의 판매/리뷰/관심도 추이가 어떤 방향인지
- 개발 시 주의해야 할 기능, 가격, 최적화, 콘텐츠, 리뷰 리스크가 무엇인지
- 어떤 근거 데이터 때문에 그런 판단이 나왔는지

최종 산출물은 인터넷 호스팅 없이 발표장에서 브라우저로 여는 정적 HTML이다. 단, 화면에 보이는 값은 하드코딩하지 않고 수집·정제·학습·분석 결과 파일에서 생성한다.

## 2. 사용자 답변으로 확정한 기준

| 항목 | 확정 기준 |
| --- | --- |
| 시연 방식 | 정적 HTML 파일을 브라우저로 열어 시연 |
| 사용자 입력 | Steam 태그/장르 체크박스 + 가격, 출시월, 언어 수, 플랫폼, 멀티플레이, 컨트롤러 등 상세 기획 입력 |
| 성공 라벨 | 장르/출시연도 내 상대 기준 중심 |
| 외부 데이터 | 웹진/평점 서비스 정보가 있으면 포함, 없거나 부족하면 해당 UI를 비활성화하고 사유 표시 |
| 모델 2 정의 | 별도 ML 모델이 아니라 모델 1 결과와 통계/유사도/리뷰 키워드를 결합한 분석·추천 엔진 |
| API 키 도구 | 무료로 키를 얻을 수 있는 도구만 후보에 포함 |

## 3. 현재 초안에서 바꿔야 하는 핵심 문제

현재 코드는 Steam 검색, appdetails, 리뷰 요약, 일부 리뷰 텍스트, 외부 웹 언급량을 수집하고 Random Forest/Logistic Regression으로 성공 여부를 분류한다. 그러나 현재 구현은 누적 리뷰 수와 누적 긍정률을 그대로 성공 라벨과 입력에 가깝게 사용하므로, “출시 초기 정보로 90일 성공을 예측한다”는 최종 설명과 맞지 않는다.

따라서 재설계에서는 다음 원칙을 고정한다.

```text
모델 입력 X:
출시 전 상점 정보 + 출시 후 7일 이내 리뷰 타임라인 지표

정답 y:
출시 후 90일 시점의 장르/출시연도 상대 성공 여부

분석 보조 지표:
SteamSpy, 웹진/평점, 현재 동접자, 현재 리뷰 총량, 현재 외부 관심도
```

90일 이후에야 알 수 있는 값이나 현재 누적 성과 값은 모델 1의 입력으로 넣지 않고, 사용자에게 보여주는 비교·설명·시장 분석 영역에서만 사용한다.

## 4. 모델/엔진 설계

### 4.1 모델 1: 성공 분류 및 성공할 장르 예측

모델 1은 머신러닝 분류 모델로 정의한다.

입력 후보:

- 가격대, 무료 여부, 할인 여부
- 장르, Steam 태그, 상점 카테고리
- 지원 언어 수
- Windows/Mac/Linux 지원 여부
- 싱글플레이/멀티플레이/협동/컨트롤러/도전과제 지원 여부
- 출시월 또는 시즌
- 출시 후 7일 리뷰 수
- 출시 후 7일 긍정률
- 출시 후 7일 리뷰 증가 속도

정답 라벨:

```text
success_90d_relative =
같은 대표 장르 + 같은 출시연도 그룹 내에서
90일 리뷰 수가 상위 25~30%이고
90일 긍정률이 최소 기준 이상인 경우
```

기본 모델 후보:

- Logistic Regression: 설명이 쉬운 baseline
- Random Forest: 비선형 관계와 feature importance 설명 가능
- 선택 확장: LightGBM 또는 XGBoost

결과 출력:

- 성공 확률
- 유사 입력 조건에서 성공률이 높은 장르/태그 조합
- feature importance
- 장르별/태그별 성공률과 표본 수
- 표본 수 부족 경고

### 4.2 모델 2: 개발자용 분석·추천 엔진

모델 2는 별도의 머신러닝 분류 모델이 아니라 모델 1과 수집 데이터 위에서 동작하는 분석·추천 엔진으로 정의한다.

구성 요소:

- 사용자 입력값 기반 유사 게임 검색
- 선택 장르/태그의 최근 성공률·리뷰 성장률·시장 규모 추이 계산
- 유사 성공작과 유사 실패작 비교
- 리뷰 텍스트 TF-IDF/n-gram 키워드 추출
- 외부 평점/웹진/SteamSpy 데이터가 있으면 보조 지표로 결합
- 데이터가 없거나 부족한 영역은 UI에서 비활성화 및 사유 표시

출력 예시:

- “현재 이 장르는 최근 표본에서 상승/유지/하락 경향”
- “유사 성공작은 평균 언어 수가 높고 컨트롤러 지원률이 높음”
- “유사 실패작의 부정 리뷰에는 optimization, bug, repetitive가 반복됨”
- “웹진 데이터 부족으로 외부 매체 관심도 분석은 비활성화됨”

## 5. 데이터 수집 계획

### 5.1 필수 데이터

| 출처 | 수집 내용 | 용도 |
| --- | --- | --- |
| Steam 검색 페이지 | appid 후보, 출시 순서, 검색 노출 데이터 | 직접 크롤링 조건 충족, 대상 게임 목록 구성 |
| Steam appdetails | 게임명, 출시일, 가격, 장르, 카테고리, 언어, 플랫폼, 기능 | 모델 입력 feature |
| Steam Reviews API | 리뷰 timestamp, 추천 여부, 리뷰 텍스트, 플레이타임 | 7일 입력, 90일 라벨, 리뷰 키워드 |
| SteamSpy | owners 추정, 평균 플레이타임 등 | 판매/시장 규모 proxy |

### 5.2 조건부 외부 데이터

| 출처 | 사용 조건 | UI 처리 |
| --- | --- | --- |
| Metacritic/OpenCritic 등 평점 서비스 | 무료·합법적 접근 가능하고 매칭 성공률이 충분한 경우 | 점수/평론가 평가 표시, 부족하면 비활성화 |
| 웹진 검색 결과 | IGN, PC Gamer, GameSpot 등에서 게임명 매칭 가능 시 | 외부 관심도와 근거 기사 표시, 부족하면 비활성화 |
| YouTube/블로그 검색 결과 | 무료 접근 가능하고 자동 수집 안정적일 때 | 관심도 proxy로만 사용 |
| 현재 동접자 | 무료 공개 엔드포인트로 확보 가능할 때 | 현재 활성도 비교용, 예측 입력에서는 제외 |

### 5.3 데이터 규모 기준

| 분석 목적 | 최소 기준 | 권장 기준 |
| --- | ---: | ---: |
| 모델 1 학습 | 유효 게임 300개 이상 | 800~1,500개 |
| 장르별 성공률 | 장르별 10개 이상 | 장르별 30개 이상 |
| 유사 게임 비교 | 후보군 300개 이상 | 후보군 1,000개 이상 |
| 리뷰 키워드 | 그룹별 리뷰 100개 이상 | 그룹별 리뷰 500개 이상 |
| 외부 웹진 관심도 | 유사 게임군 100개 이상 | 상위 후보군 중심 |

표본 수가 기준보다 작으면 결론을 숨기지 않고 “데이터 부족/해석 주의”로 표시한다.

## 6. 정적 HTML 웹사이트 설계

최종 HTML은 `reports/market_insight_site.html`로 생성한다.

필수 화면:

1. 시장 요약 대시보드
   - 최근 성공률 상위 장르/태그
   - 장르별 표본 수와 성공률
   - 리뷰 성장률/시장 규모 proxy

2. 내 게임 입력 화면
   - 장르/태그 체크박스
   - 가격대, 출시월, 언어 수, 플랫폼, 멀티플레이, 컨트롤러 등 입력
   - 정적 HTML이므로 발표용 입력 시나리오를 미리 생성된 데이터 payload에서 JS로 계산

3. 성공 가능성 및 잠재력 화면
   - 모델 1의 성공 확률
   - 선택 장르/태그의 상대 성공률
   - 성공 가능성이 높은 장르 조합
   - 근거 feature importance

4. 유사 게임 비교 화면
   - 유사 성공작/실패작 리스트
   - Steam 링크
   - 가격, 언어, 플랫폼, 리뷰 성장률, 긍정률 비교

5. 개발 주의점 화면
   - 유사 게임 리뷰의 긍정/부정 키워드
   - 개발상 주의할 항목
   - 데이터 근거와 표본 수

6. 외부 데이터 화면
   - SteamSpy, 웹진, 평점 서비스 데이터가 있으면 표시
   - 없으면 “수집 실패/매칭 부족/무료 API 없음/표본 부족” 중 사유를 표시하고 해당 카드 비활성화

## 7. 사용 승인 후보 도구

아래 도구는 계획 단계 후보이며, 실제 사용 전 승인이 필요하다.

### 7.1 우선 승인 권장

| 도구 | 용도 | 승인 필요 이유 |
| --- | --- | --- |
| Steam 공개 Store/API 엔드포인트 | appdetails, 리뷰, 현재 플레이어 등 수집 | 핵심 데이터 출처 |
| SteamSpy API | owners/플레이타임 proxy 수집 | 시장 규모 proxy 보강 |
| Playwright | 동적 페이지 또는 정적 HTML QA | 브라우저 자동화 사용 |
| Scrapy | 크롤링 규모 확장 시 안정적 수집 | 요청 관리/재시도/파이프라인 |
| pandas | 데이터 정제/집계 | 기존 사용 중 |
| scikit-learn | 모델 1 학습 | 기존 사용 중 |
| Plotly 또는 ECharts | 정적 HTML 내 인터랙티브 차트 | 발표용 UI 품질 향상 |
| Jinja2 또는 Quarto | 정적 HTML 생성 템플릿 | 하드코딩 방지 |

### 7.2 선택 후보

| 도구 | 용도 | 사용 조건 |
| --- | --- | --- |
| DuckDB | CSV/Parquet 로컬 분석 | 데이터가 커져 pandas만으로 불편할 때 |
| Pandera | 데이터 스키마 검증 | 수집 데이터 품질 검증 강화 시 |
| LightGBM/XGBoost | 모델 성능 비교 | scikit-learn baseline 이후 필요할 때 |
| MLflow | 실험 추적 | 모델 실험이 많아질 때 |
| DVC | 데이터/모델 버전관리 | 팀 단위 재현성이 중요할 때 |
| RAWG/IGDB | 외부 게임 메타데이터 | 무료 API 키 확보 가능할 때만 |
| SerpAPI 등 검색 API | 웹진 검색 안정화 | 무료 키/쿼터가 충분하고 승인된 경우만 |

### 7.3 고위험 또는 제한 후보

- Metacritic/OpenCritic 직접 크롤링: 공식 API가 없거나 약관 문제가 있으면 사용하지 않는다.
- 무제한 검색엔진 크롤링: 차단 및 약관 리스크가 있으므로 제한적으로만 사용한다.
- 유료 API: 이번 계획에서는 제외한다.

## 8. 작업 단계

### Phase 0. 현재 초안 정리

- 기존 파일 구조를 새 설계에 맞게 정리한다.
- 원천 자료와 과제 PDF는 이동하지 않는다.
- 기존 초안 산출물은 필요 시 `reports/archive/`로 보존한다.

### Phase 1. 데이터 수집 재설계

- Steam appid 후보 수집 범위를 확정한다.
- appdetails 수집을 유지·확장한다.
- 리뷰는 요약이 아니라 timestamp 포함 원본 리뷰를 페이지 단위로 수집한다.
- 출시일 기준 7일/30일/90일 리뷰 지표를 만들 수 있게 raw schema를 고정한다.
- SteamSpy와 조건부 외부 데이터 수집 모듈을 분리한다.

### Phase 2. 라벨링/피처링 재설계

- 현재 누적 리뷰 기반 `success`를 폐기하거나 보조 지표로 내린다.
- `success_90d_relative`를 주 라벨로 만든다.
- 모델 입력에서 30일/90일/현재 누적 성과 변수를 제외한다.
- 장르/태그 multi-hot encoding을 만든다.
- 표본 수 부족 경고 필드를 만든다.

### Phase 3. 모델 1 학습

- Logistic Regression과 Random Forest baseline을 학습한다.
- 가능하면 LightGBM/XGBoost는 선택 비교로 둔다.
- Accuracy보다 F1, Precision, Recall, ROC-AUC, confusion matrix를 함께 보고한다.
- feature importance와 해석 가능한 설명을 저장한다.

### Phase 4. 모델 2 분석·추천 엔진

- 사용자 입력값을 feature vector로 변환한다.
- cosine similarity 또는 KNN으로 유사 게임을 찾는다.
- 유사 성공작/실패작 평균을 비교한다.
- 리뷰 키워드와 부정 리스크를 추출한다.
- 외부 데이터 부족 시 비활성 사유를 payload에 기록한다.

### Phase 5. 정적 HTML 생성

- `reports/market_insight_site.html` 생성기를 만든다.
- 데이터 payload는 CSV/JSON 결과에서 생성한다.
- HTML 내부 JS는 미리 생성된 payload를 필터링하고 계산한다.
- 값은 코드에 고정하지 않고 결과 파일에서 읽는다.

### Phase 6. 검증 및 발표 준비

- 전체 파이프라인 재실행으로 HTML을 재생성한다.
- 모델 입력에 미래 데이터가 섞이지 않았는지 검사한다.
- HTML을 실제 브라우저로 열어 체크박스/입력/비활성 카드/Steam 링크를 확인한다.
- 최종 발표용 시나리오 2~3개를 고정한다.

## 9. 검증 시나리오 계약

작업 승인 후 실제 구현 전 아래 시나리오를 테스트 기준으로 사용한다.

### 시나리오 1: Happy path

- 조건: 사용자가 충분한 데이터가 있는 장르/태그 조합을 선택한다.
- 통과 조건: HTML이 성공 확률, 유사 성공작/실패작, 장르 트렌드, 리뷰 주의점을 표시한다.
- 검증 표면: 브라우저에서 `reports/market_insight_site.html` 열기.
- 테스트 후보: 정적 payload 생성 테스트 + HTML 파싱 테스트.

### 시나리오 2: 외부 데이터 부족 edge

- 조건: 선택한 게임/장르에 웹진 또는 평점 서비스 데이터가 부족하다.
- 통과 조건: 해당 UI 카드가 비활성화되고 “데이터 부족/매칭 실패/무료 API 없음” 중 사유를 표시한다.
- 검증 표면: 브라우저 HTML 카드 확인.
- 테스트 후보: payload의 `availability` 필드 검증.

### 시나리오 3: 미래 데이터 누수 방지

- 조건: 모델 1 학습 feature 테이블을 생성한다.
- 통과 조건: 30일/90일/현재 누적 성과 변수는 모델 입력 feature에 포함되지 않는다.
- 검증 표면: feature schema 테스트와 모델 학습 로그.
- 테스트 후보: feature column whitelist 테스트.

### 시나리오 4: 인접 회귀 방지

- 조건: 기존 파이프라인을 실행한다.
- 통과 조건: raw/interim/processed/reports/models 산출물이 생성되고, 최종 HTML에 Steam 링크와 결론이 포함된다.
- 검증 표면: `PYTHONPATH=src python3 run_pipeline.py` 및 HTML 파싱.
- 테스트 후보: pipeline smoke test.

승인되면 다음 순서로 진행한다.
